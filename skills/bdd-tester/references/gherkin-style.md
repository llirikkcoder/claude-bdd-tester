# Gherkin style

Правила, которых держится `bdd-planner` и по которым скорит `bdd-reviewer`. Не догма — если у проекта в `.bdd-config.yaml → philosophy` есть переопределения, они выигрывают.

## 1. Декларативный, не императивный

**Плохо (императив, UI-детали в сценарии):**
```gherkin
Дано пользователь открывает https://example.com/login
  И вводит "user@x.com" в поле #email
  И нажимает кнопку с текстом "Войти"
```

**Хорошо (декларатив, бизнес-намерение):**
```gherkin
Дано пользователь авторизован
```

Все клики/типизации/URL прячутся в step definitions. Сценарий отвечает на вопрос «что происходит», а не «как».

## 2. Одна поведенческая единица на сценарий

Если у сценария 3 `Then` и они про 3 разных бизнес-правила — это 3 сценария.

**Плохо:**
```gherkin
Тогда деньги возвращаются на карту
  И клиенту приходит email
  И товар помечается как возвращённый
  И бонусы списываются
```

**Хорошо (можно склеить в один Then, если это одна композитная бизнес-транзакция):**
```gherkin
Тогда возврат оформлен: деньги на карте, email отправлен, статус — "возвращён"
```

Или три сценария, если правила независимы.

## 3. Background — только для реально общих Given

Если 5 сценариев из 6 начинаются с "Дано клиент авторизован" — вынеси в `Background`. Если только 2 из 6 — не выноси, дублируй.

## 4. Конкретные значения, не абстрактные

- ❌ "недавно", "какое-то время назад", "быстро"
- ✅ "10 дней назад", "1 января 2026", "в течение 3 секунд"

Абстрактные значения = невозможно автоматизировать без домыслов.

## 5. Scenario Outline — только для табличных вариаций

```gherkin
Сценарий: <название>
  Дано клиент купил товар <дней> дней назад
  Когда он оформляет возврат
  Тогда получает <результат>

  Примеры:
    | дней | результат           |
    |    5 | одобрен             |
    |   14 | одобрен             |
    |   15 | отказ (просрочен)   |
```

Не используй Outline, если Given/When различаются между строками — это не один сценарий, а разные.

## 6. Пиши как продакт, не как программист

Каждый шаг — предложение на человеческом языке. Никаких:
- `Дано database has row {id: 42, status: 'active'}`
- `Когда endpoint POST /api/v2/returns вызван`
- `Тогда response.body.data.status == 'ok'`

Продакт должен уметь прочитать и подтвердить/оспорить.

## 7. Актив, не пассив; настоящее время

- ❌ "деньги должны быть возвращены"
- ✅ "деньги возвращаются на карту в течение 3 дней"

Настоящее — короче, читабельнее, точнее.

## 8. И (And) — для нанизывания однородных

```gherkin
Дано клиент авторизован
  И у клиента есть купленный товар
  И товар куплен 10 дней назад
```

Не начинай сценарий с `И` — только продолжение.

## 9. Тэги — для среза, а не мета-данных

Хорошие тэги: `@critical`, `@smoke`, `@slow`, `@wip`, `@requires-payment-gateway`.
Плохие тэги: `@ticket-1234`, `@author-kirill`, `@created-2026-08` (это в git и в metadata frontmatter).

### 9.1. `@pending-*` теги для честного маркирования незакрытых OQ

**Проблема.** В pre-code discovery часто рождается сценарий с конкретным значением (порог < 5 слов, «календарный день», «3 упоминания подряд»), которое сам планер помечает как open_question. Если оставить значение без метки — сценарий **молча закрывает OQ**, и через месяц никто не помнит, что этот порог был условным допущением, а не решением продукта.

**Решение.** Помечать такие сценарии тегом `@pending-<КОД>` с явной ссылкой на open_question. Ревьюер обязан выставлять `must_fix`, если видит зашитое значение из открытого OQ без соответствующего тега.

**Конвенция именования:**

- `@pending-OQ<N>` — сценарий полагается на неотвеченный OQ#N
- `@pending-threshold-OQ<N>` — конкретный числовой порог из OQ#N (порог < 5 слов, 20 слов, 3 дня, 14 дней)
- `@pending-clinical` — требует валидации клинического консультанта (не запускать в prod без sign-off)
- `@safe-by-default` — сценарий фиксирует консервативную трактовку неоднозначного случая (например «неоднозначный ответ = отказ»)
- `@critical` — критический сценарий (клинический редирект, платёж, необратимое действие)

Пример:
```gherkin
@pending-threshold-OQ4
Сценарий: Инсайт-паттерн для активной серии из 3+ дней подряд
  Дано пользователь проходил чек-ин 2 дня подряд без пропусков
  Когда пользователь завершает третий чек-ин подряд
  Тогда аватар выдаёт итоговый инсайт...
```

Читатель видит тег → идёт в раздел `# ОТКРЫТЫЕ ВОПРОСЫ` → находит OQ#4 (с какого дня появляется инсайт-паттерн — условно 3) → знает, что «3» это допущение, не решение.

**Как ревьюер их проверяет:**

Для каждого сценария с конкретным пороговым значением ревьюер проверяет: (а) есть ли соответствующий OQ в блоке открытых вопросов? (б) если да — есть ли `@pending-*` тег? Если OQ есть, а тега нет — `must_fix`.

**Что снимают теги:**

- `@pending-*` снимаются, когда OQ закрыт продуктом. Порог `< 5 слов` подтверждён → `@pending-threshold-OQ1` убирается, соответствующий пункт удаляется из блока open_questions в конце файла.
- `@pending-clinical` снимается ТОЛЬКО после письменного sign-off клинического консультанта.

**Что тегами НЕ решается:**

Теги — маркер честности, а не замена ответа. Если у сценария 4 `@pending-*` тега — это сигнал вернуться к продукту, а не радоваться, что «всё помечено».

## 10. Feature = одна user story

Один `.feature` файл на одну связную историю. 3–10 сценариев в нём — норма. 20+ — режь на несколько features.

## Anti-patterns (auto-flag на ревью)

- Императивные UI-шаги ("клик на кнопку X")
- Разные бизнес-правила в одном сценарии
- Абстрактные значения ("recently", "shortly")
- Технический жаргон ("endpoint", "row", "response.body")
- Условия внутри шага ("если пользователь авторизован, тогда...") — расщепи на сценарии
- Гигантские Background (>5 шагов)
- `Then` без `When`
- Сценарии, зависящие от порядка выполнения
