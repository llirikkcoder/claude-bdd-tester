# BDD vs TDD vs unit-tests — когда что

Не всё нужно оборачивать в Given-When-Then. Ниже — честная матрица «когда BDD, когда unit-tester, когда оба».

## Одноосное правило: **читает ли сценарий не-технарь?**

- Если **да** (продакт, юрист, medical affairs, клиент) → BDD оправдан
- Если **нет** (только разработчик) → unit-tests + mutation-testing (см. `unit-tester` skill), BDD — оверинжиниринг

## Матрица

| Что тестируем | Инструмент | Почему |
|---|---|---|
| Пользовательская воронка (форма → email → оплата) | **BDD + Playwright** | e2e-контракт, читает продакт |
| Онбординг / регистрация / рефлексия | **BDD** | user-facing, критично для метрик |
| Бизнес-правила с ветвлением (промо-коды, тарифы) | **BDD** | продакт/маркетинг задают правила |
| Отдельная pure-функция / модуль | **unit-tester** | нет бизнес-стейкхолдера, BDD = шум |
| Refactor-safety на хелперы | **unit-tester + mutation** | покрытие кода, не поведение |
| API-контракт для внешнего клиента | **BDD** (contract-BDD) | клиент читает |
| LLM-качество / RAG-recall | **RAGAS + PPI + GT** | статистика, не boolean |
| Регуляторный User Requirements Spec (GxP/HIPAA) | **BDD** | Gherkin ≈ URS-документ, аудитор читает |
| Perf/nonfunctional | **отдельные profiler-тесты** | BDD плохо ложится на численные метрики |
| Security (OWASP LLM, prompt-injection) | **adversarial + security-review** | тесты не ловят по определению |
| Микросервисная интеграция | **contract-tests (Pact)** или **BDD** | зависит от того, кто читает |

## Комбинированный подход

Часто правильный ответ — **и то, и другое**:
- BDD на верхнем уровне: пользовательский путь оплачен и подтверждён
- unit-tester внутри: `RefundCalculator._compute_arrival_date(...)` покрыт бранч+мутациями

BDD-сценарий ловит «эта фича работает end-to-end», unit ловит «эта конкретная функция не сломана». Разные слои.

## Не путать BDD с

- **Тестами на UI без бизнес-читаемости** — если сценарий начинается с "клик на кнопку с id #submit-btn", это Selenium-скрипт, не BDD
- **Snapshot-тестами** — snapshot всегда зелёный на не-багах и всегда красный на форматировании; BDD assert-ит наблюдаемое поведение
- **Post-hoc документацией** — сценарий, написанный после кода, теряет главное свойство (протоколирует существующее вместо задания контракта)

## Красные флаги — BDD не поможет

- Стейкхолдер не читает и не будет — только вы
- Продукт data-heavy (ETL, ML-обучение, batch-джобы) — G-W-T плохо ложится
- Проект в исследовательской стадии, требования меняются каждую неделю — сценарии будут гнить быстрее, чем стабилизироваться
- Нет CI и не будет — BDD без автопрогона = мёртвая документация, тот же груз что дохлые спеки в SDD (проблема, ради которой BDD и появился — см. заметку в vault)

## Как решить в спорном случае

Задай 3 вопроса:
1. **Читатель кроме меня?** Нет → unit-tester.
2. **Регрессия ломает деньги/UX/юридику?** Нет → unit-tester + мутации.
3. **Требования формулируются на человеческом языке в тикетах/PRD?** Нет → unit-tester.

Три "нет" — просто пиши unit-tests.

## Для AZ-RAG (частный кейс)

- **backend/eval/retrieval** — unit-tester (то, что уже собрано).
- **chat UI** (если есть) — BDD может быть уместен для 5–10 критических сценариев (safety warnings, source citation, refusal on off-topic).
- **GxP User Requirements** — BDD может быть уместен как двойная запись (Gherkin + аудитор его читает).
- **RAG-recall / faithfulness** — НЕ BDD, а RAGAS + PPI + GT (уже построено, [[project-az-rag-stack]]).

## Универсальный совет

Начинай малой кровью: 5–10 сценариев на самое дорогое поведение. Если через месяц эти сценарии стали живой документацией, которую продакт открывает и обсуждает — расширяй. Если открывал 1 раз для галочки — сворачивай.
